# 08 — Genesis & Configuration

## Overview

Genesis in Tempo is generated by the `xtask` crate's `genesis_args.rs`. The process is deterministic given the same inputs, ensuring all nodes produce identical genesis blocks.

---

## Genesis Generation Process

### L1 Genesis

The genesis generation process (`tempo/xtask/src/genesis_args.rs`):

1. **Generate accounts** — 50,000 accounts from mnemonic (default)
2. **Deploy Arachnid CREATE2 factory** — At `0x4e59b44847b379578588920cA78FbF26c0B4956C`
3. **Deploy Permit2** — At `0x000000000022d473030f116ddee9f6b43ac78ba3`
4. **Initialize TIP403 Registry** — Permissioned token compliance
5. **Initialize TIP20 Factory** — Token creation
6. **Create pathUSD token** — At reserved address `0x20C0...`
7. **Optionally create AlphaUSD, BetaUSD, ThetaUSD** — Additional stablecoins
8. **Generate consensus config** — DKG output, signing keys/shares
9. **Initialize ValidatorConfigV2** — All validators
10. **Initialize Fee Manager** — Default fee tokens
11. **Initialize StablecoinDEX** — Fee AMM
12. **Initialize NonceManager** — 2D nonce system
13. **Initialize AccountKeychain** — Passkey/WebAuthn
14. **Initialize AddressRegistry** — Name/address mapping (T3+)
15. **Initialize SignatureVerifier** — Signature verification (T3+)
16. **Initialize ReceivePolicyGuard** — Receive policy (T6+)
17. **Mint pairwise FeeAMM liquidity** — pathUSD/AlphaUSD, etc.
18. **Insert ZoneFactory state** — T10+
19. **Deploy Multicall3, CreateX, SafeDeployer** — Standard Ethereum contracts
20. **Deploy EIP-2935 history storage** — Block hash history
21. **Write DKG outcome** — Into genesis header `extra_data`

### L2 Zone Genesis

Zone genesis (`zones/xtask/src/`) anchors to a finalized Tempo block:

1. **Anchor to finalized block** — Deterministic initialization
2. **Domain-separate chain ID** — Prevent replay attacks
3. **Deploy system predeploys:**
   - pathUSD (`0x20c0...`)
   - ZoneInbox (`0x1c00...0000`)
   - ZoneOutbox (`0x1c00...0002`)
   - TIP403Registry
   - NonceManager
   - ZoneFeeManager
   - Multicall3
   - UniversalRouter
   - Create2Factory
4. **Configure fee token** — pathUSD, 6 decimals
5. **Initialize storage** — Fee configuration

### L2 Zone Chain IDs

Zone chain IDs are **domain-separated** from the parent L1 chain ID to prevent replay attacks.

Example: Zone on L1 chain ID 17 → Zone chain ID = `17 + offset` (specific formula in `zone-chainspec`).

## Hardfork Schedule

Tempo defines 16 hardforks in the `TempoHardfork` enum:

```rust
enum TempoHardfork {
    Genesis,
    T0,
    T1,
    T1A,
    T1B,
    T1C,
    T2,
    T3,
    T4,
    T5,
    T6,
    T7,
    T8,
    T9,
    T10,
    T11,
    T12,
}
```

### Activation

Each hardfork activates at a configurable **timestamp**:

```bash
--t0-time 1234567890 \
--t1-time 1234567891 \
--t2-time 1234567892 \
...
--t12-time 9999999999  # Far future (disable T12)
```

### Hardfork Features

| Hardfork | Key Features |
|----------|--------------|
| **Genesis** | Initial state, basic precompiles |
| **T0** | Base fee = 10B attodollars |
| **T1** | TIP-1000 gas costs, base fee = 20B attodollars |
| **T1A** | Per-tx gas cap = 30M |
| **T1B** | Minor adjustments |
| **T1C** | Minor adjustments |
| **T2** | Validator Config V2 precompile |
| **T3** | Address Registry, Signature Verifier |
| **T4** | TIP-1016 gas split (disabled), shared gas limit = 0 |
| **T5** | TIP20 Channel Reserve |
| **T6** | Receive Policy Guard |
| **T7** | TIP-1060 storage credits, TIP-1067 dynamic base fee |
| **T8** | Current Committee precompile |
| **T9** | Minor adjustments |
| **T10** | Zone Factory, zone system |
| **T11** | Expiring nonce capacity |
| **T12** | Latest hardfork |

### ThaiFi Fork Custom Flags

The ThaiFi fork adds custom flags not in upstream:

```bash
--zone-factory-owner <ADDR>     # Custom ZoneFactory owner
--genesis-timestamp <UNIX>      # Chain start time
--gas-token-name <NAME>         # Gas token name
--gas-token-symbol <SYMBOL>     # Gas token symbol
--gas-token-currency <CURRENCY> # Gas token currency
```

These flags allow customization of the genesis state without modifying hardcoded values.

## Validator Configuration

### Validator Registration

At genesis, validators are configured via `ValidatorConfigV2`:

```rust
struct Validator {
    ed25519_key: Ed25519PublicKey,      // P2P identity
    signing_share: Bls12381SigningShare, // Threshold signing
    address: Address,                    // On-chain address
    ingress: String,                     // Ingress endpoint
    egress: String,                      // Egress endpoint
    fee_recipient: Address,              // Fee recipient
}
```

### Registration Signature

Validators must sign:
```
chainId || contractAddr || validatorAddr || ingress || egress || feeRecipient
```

This proves ownership of the Ed25519 key and binds it to the on-chain identity.

## DKG at Genesis

At genesis, the DKG (Distributed Key Generation) output is written into the genesis header's `extra_data` field:

```rust
struct GenesisExtraData {
    dkg_outcome: DkgOutcome,
    scheme: SchemeProvider,
}
```

This allows all nodes to verify the initial validator set's threshold keys.

---

## Key Constraints

1. **Deterministic genesis** — Same inputs → same genesis block
2. **Hardfork timestamps** — All hardforks activated by timestamp, not block number
3. **T10 for zones** — Zone Factory activates at T10; T11/T12 breaks zone compatibility
4. **USD currency required** — Gas token must have `currency="USD"`
5. **ZoneFactory owner** — ThaiFi fork allows custom owner; upstream hardcodes
